The original detailed phased plan is preserved without loss in [`TODO-DETAILED.md`](TODO-DETAILED.md). Use that file for the complete historical checklist, phase-specific implementation notes, and long-range backlog. Use this file to decide what work happens next.

## Status convention

- `[ ]` Work remains to be completed.
- `[X}` Work is completed.

The completed marker intentionally follows the project convention requested for this repository.

## Priority convention

- **P0 — Current critical path.** Work that establishes the product experience, prevents expensive rework, or is required for the next credible demonstration.
- **P1 — Next connected value.** Work that becomes actionable as its real data sources and domain contracts are available.
- **P2 — Later platform expansion.** Important work that must not delay the assurance MVP.

A priority does not override safety, accessibility, testing, or truthful-data requirements. A visually polished feature is not complete if it invents evidence, hides unsupported states, or cannot be operated with a keyboard and assistive technology.

  1. Audited this pass rather than assumed. **The signal-based reactive architecture is already real and pervasive, so this is mostly a "keep doing this" note with one genuine gap.** What exists today:

- [X} Signals as the single state representation. `WorkspaceService` holds 26 `signal()`/`computed()` members; every view derives from them rather than holding its own copy. No component caches a snapshot into a plain field, so nothing can go stale relative to the service.

Two real ones were found by audit and fixed, both in code that recomputes on every dependency change: `ComponentInventoryService.result` rebuilt the whole Storybook story index once _per component_ (now `createStoryIndexLookup` builds it once per recompute — O(components × storyEntries) → O(components + storyEntries)), and `computeChangeImpact` re-scanned every discovery's `sourceFiles` for every changed file (now an inverted `Map` built once). Deliberate design choices: watched directories are derived from already-scanned real data (`computeWorkspaceWatchDirectories` in `apps/forgegate-desktop/src/app/workspace-watch-directories.ts`, from `componentPackages`/`tokenFiles`/`uiSourceFiles`), so `node_modules`/`.git`/`dist` are excluded _by construction_ rather than by filtering, and nested watch roots collapse to their shared parent. Two real engineering problems were found and fixed along the way, both specific to this environment: depending on `tauri`'s `"test"` feature to unit-test against a real Tauri event bus broke the entire Rust test binary on Windows with `STATUS_ENTRYPOINT_NOT_FOUND` (a `wry`/WebView2 DLL entry-point failure under bare `cargo test`) — fixed by keeping the watcher's core logic fully Tauri-free (a plain callback, tested with `std::sync::mpsc`) and confirming that pattern generalizes: don't reach for `tauri::test` for unit-level Rust tests in this codebase. Second, an initial debounce-coalescing test assumed a rapid burst of writes always arrives as one batch; real runs (confirmed by writing up to 60 files) showed Windows/`notify` can split a burst into multiple raw flushes even inside one nominal debounce window, so the deterministic path-sort/dedup/truncate/cap logic was pulled into a pure `build_changed_event` function and tested with synthetic event batches, keeping only two real end-to-end OS tests (basic detection, directory scoping) for what genuinely needs the real OS. 75/75 Rust tests passing (was 66), 294/294 desktop tests passing (was 275).

### Persistence and longitudinal tracking

**Goal:** ForgeGate should track each scanned repository's assurance posture _over years_, not just render the current scan. Today every signal is in-memory and dies with the process — the app cannot answer "is this design system getting better?", which is the question a federal/regulated buyer actually cares about at renewal time. This is a real product capability, not just an infrastructure chore, and it also unblocks several gaps tracked above (P1.3's real evidence timeline, P1.2's real readiness split, and "mark prior approval stale after a relevant source change" in the MVP definition of done).

**Decision (supersedes this section's earlier SQLite-first plan): skip SQLite entirely and go straight to PostgreSQL in Docker.** Since there is no SQLite to migrate _from_ (nothing persists at all today), an intermediate SQLite step would be a schema and a data-access layer built specifically to be thrown away. Longitudinal tracking across years — and eventually across a team or CI feeding one shared record per repository — is a server-database problem, so building directly against the real target avoids paying for the migration twice.

**The one real tradeoff, and how it is handled:** ForgeGate is a local-first Tauri desktop app, and requiring Docker + Postgres just to launch it would be a significant regression. So **persistence is opt-in**: with no database configured the app behaves exactly as it does today (in-memory signals, current scan only, nothing persisted). Configuring a database adds history; it is never required to use the product. That keeps "local-first" true for the single-user case without needing a second storage engine to prove it.

- [X} **Docker Compose Postgres for development, with real migrations from the first commit.** `docker/dev-compose.yml` defines a health-checked Postgres 17 service on local port 54329, root package scripts expose non-destructive `db:up`/`db:ps`/`db:logs`, and `apps/forgegate-desktop/src-tauri/migrations/0001_evidence_history.sql` creates the first schema through the Rust migration runner.
- [X} **Persist scan snapshots and derived per-component rows, not just current state.** When `FORGEGATE_DATABASE_URL` is set, `read_workspace_scan` appends the raw workspace scan JSON into Postgres and never requires the database when the variable is unset; once Angular finishes the component inventory, ForgeGate updates that latest snapshot with source commit, dirty state, component count, lifecycle counts, derived readiness summary, adapter status summary, and one `component_snapshots` row per component. `component_snapshots` are deliberately derived below a scan snapshot and replaced idempotently for that scan id during enrichment, while the scan itself remains append-only. Each component row records id, optional version, framework, adapter, lifecycle, source files, derived readiness, and a structured `finding_summary`.
- [X} **Derive real per-component readiness/finding states.** Current scans now compute `blocked`, `stale`, `warning`, and `clear` from the same component-local evidence gaps shown in the detail/export path: missing state/story/token/test/manual/docs connections warn, failed or blocked automated evidence blocks, stale automated/documentation evidence is stale, and components with no derived findings are clear. Still open: durable event sourcing for manual-review/release-decision changes and causal stale-evidence explanations.
- [X} **A dev seeding file that replays progress over time on the two sample repos.** `apps/forgegate-desktop/src-tauri/seeds/dev_evidence_history.sql` seeds 12 replaceable rows across `public-sector-federation` and `phase-2-cosmic`, spanning January-June 2026 with plausible component-count, lifecycle, adapter-status, dirty-state, and commit progression. Every row is `seeded = true` with `seed_label = 'dev-history-2026-07'`, and rerunning the seed deletes/replaces only rows with that label. Root script `db:seed` applies it through the Compose Postgres container; a Rust unit test guards that the file stays unmistakably seeded and covers both sample repos.
- [X} **Real trend views over that history.** `read_evidence_history_trend` queries the opt-in Postgres store for the selected workspace, tolerating Windows slash differences so seeded `D:/...` rows match native `D:\...` selections. `EvidenceHistoryTrendView` renders the persisted scan sequence on `/workspace`: snapshot count, latest component count, component delta, per-scan component bars, readiness bucket text, adapter loaded/partial counts, commit, dirty state, and explicit seeded-row labels. It handles unconfigured persistence, connection failures, and empty history distinctly; focused Angular tests cover all three UI states, and an ignored disposable-Postgres Rust test covers the real SQL trend query.
- [ ] **pgvector — a real possibility, but for a different problem than longitudinal tracking.** Worth stating plainly so it doesn't get planned into the wrong slot: trend-over-time queries ("readiness by month", "when did this go stale") are ordinary relational time-series work — pgvector adds nothing there, and reaching for it would be cargo-culting. Where embeddings _would_ genuinely help is semantic search and similarity across the inventory: "find components across our repos that look like this one" (near-duplicate detection across a large or multi-repo design system), "which existing component already covers this need" before someone builds a fourth button, or matching a component to relevant guidance/procedure text.
